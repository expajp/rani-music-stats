# RaNi Music Stats 要件定義書

- 版：第2版（2026-10-10）
- ステータス：ドラフト
- 実現方法は `docs/design.md`（設計書）に書く

## このサービスで何を実現するのか

ラジオNIKKEI第2「RaNi Music」で流れた曲を毎日記録する。記録したデータを、統計の参照と曲の絞り込みができる静的サイトで公開する。

利用者は自分（オーナー）だけを想定する。目的は、新しく流れ始めた曲や、よく流れるのに知らない曲を見つけて、自分のプレイリストを充実させることにある。

「知らない曲」かどうかの判定はオーナーが行う。サービスでは扱わない。

## 記録の対象はどの放送か

- 放送局：ラジオNIKKEI第2
- 放送時間：平日 08:30〜19:00（10時間30分）
  - 祝日も、土日でなければ放送する
  - 再放送はない
- 対象の枠：番組名に `RaNi Music` を含む枠だけを対象にする
  - 放送時間中にも音楽以外の番組が入ることがある。番組名で判定するので、祝日や特番のカレンダーを別に持つ必要はない

## 曲のデータはどこから取得するのか

### 曲名・アーティスト・オンエア時刻は公式オンエアリストから取る

公式サイトの「楽曲 ON AIR リスト」（`https://www.radionikkei.jp/ranimusic/onair/`）は、日付ごとのJSON（`https://www.radionikkei.jp/json/YYYYMMDD.json`）を読み込んで表示している。このJSONを取得元にする。

2026-10-10 に調べた、このJSONの性質は次のとおり。

- 曲名とアーティストが別々の項目に入っている
- オンエア時刻は秒まで入っている
- 番組の区切り（番組名と放送時間の範囲）も、曲と同じ配列に混ざっている
- 発表年は入っていない
- 1年以上前の日付（2025-10-01）も取得できた
- 2日先までの日付も取得できた。4日先は 403 を返した
- 海外IP（GitHub Actions）からも取得できた
- robots.txt で `/json/` は禁止されていない

radiko タイムフリーの番組説明文にも曲目と発表年が載っている。しかし、次の理由で使わない。

- 遡れるのが7日間だけ
- 12:00〜13:08 の「All Request Hour」の曲が載らない（2026-10-09 では公式JSONの157曲に対して140曲）
- 海外IPには説明文を返さない。国内で動く実行環境（AWS Lambda など）が別に必要になる

### 発表年は iTunes Search API から取る

公式JSONに発表年がないので、iTunes Search API（Apple の公開API。認証不要）で曲名とアーティストを検索し、上位5件のうち曲名がいちばん近い結果の発売日から年を取る。曲名が一致する結果がない曲は、別の曲の年を取らないよう「不明」とする。

2026-10-10 に、radiko の説明文にある年を正解として、検索結果の1件目を使う方式で40曲を照合したところ、35曲が一致した。残りの5曲は次のとおり。

- シングルとアルバムで年が違い、1〜2年ずれたもの：2曲
- 1件目に別の曲がヒットしたもの：1曲
- 2件目以降に正しい年があったもの：2曲

5件から選ぶ方式に変えたあと、同じ方法で61曲を照合したところ、51曲が一致した（1件目を使う方式では50曲）。ライブ版や再発盤の年を取る誤りが減り、別の曲がヒットした2曲は「不明」になった。残った誤りは、iTunes 側の発売日が実際と違うものが中心である。

目的は「知らない曲を見つける」ことなので、この精度を受け入れる。間違った年は、オーナーが手で上書きできるようにする。

検索結果がない曲は、発表年を「不明」とする。

### 取得は GitHub Actions で毎日実行し、取りこぼしを自動で補う

- 実行環境：GitHub Actions
  - 公式JSONと iTunes Search API は、海外IPから取得できることを確かめた
- 実行時刻：平日の 19:00〜23:59（JST）のあいだに1回
- 取得範囲：実行のたびに、直近7日間のうちまだ保存していない日をすべて取得する
  - 1日失敗しても、次回以降の実行で回収できる
  - 土日など、対象の枠がない日のデータは集計に使わない
- 初回の取り込み：サービス構築時に、過去1年ぶんを取得する
  - 公式サイトへのリクエストは1日1回、iTunes へのリクエストは曲ごとに1回で、どちらも間隔を空けて実行する
  - 運用開始後に、それより前のデータを遡って取得することはしない
- 取得したデータは、このリポジトリに commit する。commit をきっかけに、サイトのデプロイを実行する

## 何をデータとして持つのか

### 保存するオンエアデータ

公式JSONから、集計に必要な項目（オンエア時刻・曲名・アーティスト）だけを取り出し、日付ごとに1ファイルとして保存する。公式JSONそのものは保存しない。公開されているデータを丸ごと複製して持つことを避けるためである。

曲の判定や集計のルールを後から直したときは、公式JSONを取り直して作り直す。

### 発表年のデータ

曲ごとに、iTunes Search API の結果と、そこから取った年を保存する。結果がない曲も「検索済みで結果なし」として保存し、毎回検索し直さないようにする。

オーナーが手で直した年は、別のファイルに持ち、iTunes の結果より優先する。

### オンエアデータから作る曲のデータ

曲ごとに次の項目を持つ。

- 曲名
- アーティスト
- 発表年（不明のこともある）
- 初回オンエア日：記録している範囲で、その曲が初めて流れた日
- オンエアの履歴（日時のリスト）

曲のデータはオンエアデータから計算で作る。オンエアデータと発表年のデータだけを正として、曲のデータは保存しない。

### 同じ曲かどうかの判定

表記ゆれ（全角と半角、空白、大文字と小文字）を正規化した「曲名＋アーティスト」が一致すれば、同じ曲とみなす。正規化の詳しいルールは設計書で決める。

## サイトで何ができるのか

### 期間を指定して曲を絞り込む

- 期間（開始日〜終了日）を指定する
- 次の条件で絞り込む
  - 曲名
  - アーティスト
  - 発表年（範囲で指定する）
    - 発表年が不明の曲は、範囲を指定したときは除外する
  - 期間内に初めて流れた曲だけに絞る
- 一覧には次の項目を表示する
  - 曲名
  - アーティスト
  - 発表年（不明の曲は「不明」と表示する）
  - 期間内のオンエア回数
  - 初回オンエア日
- 一覧は各項目で並べ替えられる

### 期間内のオンエア回数を棒グラフで見る

- 期間を指定し、オンエア回数が多い順に上位 N 曲を棒グラフで表示する
  - N の初期値は30とする
- 絞り込みの条件（アーティスト・発表年など）は棒グラフにも反映する

## どこで公開するのか

- GitHub Pages で公開する
  - このリポジトリは public である
  - データの commit を受けて、GitHub Actions でビルドとデプロイを実行する
- 著作権や利用規約の面で問題がある場合は、公開方法を見直す
