# RaNi Music Stats 要件定義書

- 版：初版（2026-10-10）
- ステータス：ドラフト

## このサービスで何を実現するのか

ラジオNIKKEI第2「RaNi Music」で流れた曲を毎日記録する。記録したデータを、統計の参照と曲の絞り込みができる静的サイトで公開する。

利用者は自分（オーナー）だけを想定する。目的は、新しく流れ始めた曲や、よく流れるのに知らない曲を見つけて、自分のプレイリストを充実させることにある。

「知らない曲」かどうかの判定はオーナーが行う。サービスでは扱わない。

## 記録の対象はどの放送か

- 放送局：ラジオNIKKEI第2（radiko の局ID：`RN2`）
- 放送時間：平日 08:30〜19:00（10時間30分）
  - 祝日も、土日でなければ放送する
  - 再放送はない
- 対象の枠：番組名に `RaNi Music` を含む枠だけを対象にする
  - 放送時間中にも音楽以外の番組が入ることがある。番組名で判定するので、祝日や特番のカレンダーを別に持つ必要はない

## 曲のデータはどこから、どう取得するのか

### データ源は radiko タイムフリーの番組説明文

radiko タイムフリーの番組ページ（例：`https://radiko.jp/#!/ts/RN2/20261009171000`）の説明文にプレイリストが載る。説明文は放送中に用意される。

説明文の書式は次のとおり。

```
▼この時間のプレイリスト▼

8:30 Golden/HUNTR/X (2025年)
8:33 A New Day/Beverly (2018年)
...
（洋楽：50%　邦楽：50%）
```

公式サイトのオンエアリスト（`https://www.radionikkei.jp/ranimusic/onair/`）は発表年を含まないため、使わない。

### 取得にはヘッドレスブラウザを使う

radiko のページは JavaScript で描画する SPA なので、ヘッドレスブラウザ（Chromium）で描画してから説明文を読み取る。

### 説明文の各行を曲データに分解する

プレイリストの1行は `H:MM 曲名/アーティスト (YYYY年)` の形をしている。各行から次の項目を取り出す。

- オンエア時刻（`H:MM`）
- 曲名
- アーティスト
- 発表年

分解するときは次のルールに従う。

- 曲名とアーティストは**最後の `/` で区切る**
  - 曲名やアーティスト名自体が `/` を含むことがある（例：`Golden/HUNTR/X`、AC/DC）
  - 最後の `/` で区切るルールでも、アーティスト名が `/` を含む場合は誤る。この問題の扱いは未決事項に挙げる
- `feat.` は曲名の側に入る（例：`The Way feat. Mac Miller/Ariana Grande`）。そのまま曲名の一部として扱う
- `（洋楽：50%　邦楽：50%）` の行は使わない
- 書式に合わない行は捨てずに記録し、取得処理のログに出す

### 取得処理は国内のIPから実行する

radiko は IP アドレスで地域を判定し、海外からのアクセスには説明文を含まない内容を返す。2026-10-10 に次のとおり検証した。

| 実行環境 | 地域判定 | 説明文の取得 |
|---|---|---|
| ローカル（東京） | `JP13` | できた |
| GitHub Actions（米国） | `OUT` | できなかった |
| AWS Lambda（ap-northeast-1） | `JP13` | できた |

この結果から、取得処理は **AWS Lambda（東京リージョン、ap-northeast-1）** で実行する。

### 取得は毎日19時以降に実行し、取りこぼしを自動で補う

- 実行時刻：毎日、放送終了後の 19:00〜23:59（JST）のあいだに1回
  - 起動には EventBridge Scheduler を使う
  - 説明文は放送中に用意されるので、当日中に取得できる
- 取得範囲：実行のたびに、**直近7日間のうちまだ保存していない枠**をすべて取得する
  - タイムフリーで遡れるのは7日間なので、1日失敗しても次回以降の実行で回収できる
  - 土日など、対象の枠がない日は何もしない
- 初回の取り込み：サービス構築時の最初の実行で、直近7日間ぶんを取得する
  - 運用開始後に、7日より前のデータを遡って取得することはしない

### 取得したデータを Git リポジトリに格納する

- Lambda から GitHub API を使って、データファイルをこのリポジトリに commit する
- GitHub への認証には、このリポジトリの Contents 書き込みだけを許可したトークン（fine-grained personal access token）を使う
  - トークンは AWS Secrets Manager か SSM Parameter Store に保管する
- データの commit をきっかけに、サイトのデプロイを実行する

## 何をデータとして持つのか

### 保存する生データ

枠ごとに次の項目を保存する。

- 放送日
- 枠の開始・終了日時
- 番組名
- 説明文の原文
  - パースのルールを後から直したときに、取り直さずに作り直せるようにするため
- 分解済みの曲のリスト（オンエア時刻・曲名・アーティスト・発表年）

ファイルの単位は1日1ファイルとする（例：`data/onair/2026/2026-10-09.json`）。

### 生データから作る曲のデータ

曲ごとに次の項目を持つ。

- 曲名
- アーティスト
- 発表年
- 初回オンエア日：サービス構築以来、その曲が初めて流れた日
- オンエアの履歴（日時のリスト）

曲のデータは生データから計算で作る。生データだけを正として、曲のデータは保存しない。

初回の取り込みで入った曲は、すべて「その週に初めて流れた曲」になる。運用開始から数週間は「初めて流れた曲」が実際より多く見える。この偏りは仕様として受け入れる。

### 同じ曲かどうかの判定

表記ゆれ（全角と半角、空白、大文字と小文字など）を正規化した「曲名＋アーティスト」が一致すれば、同じ曲とみなす。正規化の詳しいルールは未決事項に挙げる。

## サイトで何ができるのか

### 期間を指定して曲を絞り込む

- 期間（開始日〜終了日）を指定する
- 次の条件で絞り込む
  - 曲名
  - アーティスト
  - 発表年（範囲で指定する）
- 一覧には次の項目を表示する
  - 曲名
  - アーティスト
  - 発表年
  - 期間内のオンエア回数
  - 初回オンエア日
- 一覧は各項目で並べ替えられる

### 期間内のオンエア回数を棒グラフで見る

- 期間を指定し、オンエア回数が多い順に上位 N 曲を棒グラフで表示する
  - N の初期値は30とする
- 絞り込みの条件（アーティスト・発表年など）は棒グラフにも反映する

## どこで公開するのか

- 第一候補：GitHub Pages
  - データの commit を受けて、GitHub Actions でビルドとデプロイを実行する
- 著作権や利用規約の面で問題がある場合：Claude Artifacts で公開する

## 未決事項

### 公開と規約について

- radiko の利用規約で、自動取得がどう扱われているかを確認する
  - radiko の robots.txt は番組表API（`/v3/`）をクローラーに対して Disallow にしている。ヘッドレスブラウザでページを開く場合も、裏で同じAPIを呼ぶ
- GitHub Pages で公開してよいかを判断する
  - 曲名・アーティスト・放送日時は事実の情報で、著作権では保護されにくいと考える。ただし公開前に、各サイトの規約を確認する
- このリポジトリは private である。private リポジトリで GitHub Pages を使うには有料プラン（GitHub Pro など）が必要になる。また、Pages で公開したサイト自体は誰でも見られる
- Artifacts で公開する場合、毎日の自動デプロイをどう実現するか
  - Artifacts は Claude 経由で公開するので、Lambda や Actions からの自動更新とは相性が悪い

### データの扱いについて

- アーティスト名が `/` を含む場合（例：AC/DC）の分解方法
  - 既知のアーティスト名の例外リストを持つ案などがある
- 同じ曲と判定するための正規化ルール
  - 例：全角と半角の統一（Unicode の NFKC 正規化）、空白の統一、大文字と小文字の区別
- 同じ曲が異なる発表年で流れた場合（リマスター版など）の扱い
  - 別の曲とするか、同じ曲として発表年を複数持つか

### 運用について

- 取得に失敗したことに、どうやって気づくか
  - 例：CloudWatch のアラーム、GitHub Issue の自動作成
- サイトの技術スタック（フレームワーク、グラフのライブラリ）

### 今後の検討

- 各曲に Spotify や Apple Music の検索リンクを付け、プレイリストに追加するまでの手間を減らす
